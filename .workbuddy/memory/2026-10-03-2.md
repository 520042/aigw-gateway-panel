## 一、网页问题（真凶：app.js 语法错误）

**症状**：页面卡在「正在加载…」，`view` 容器始终为空，`window.S` 不存在。

**定位过程**：
1. `agent-browser` 首次 `open` 卡在下载 Chromium，超时 → 先用静态校验
2. Chromium 就绪后 `eval` 抓状态：`S存在:false | view innerHTML长度=0`
3. `fetch('/app.js')` + `eval` 拿到异常：**`SyntaxError: Missing initializer in const declaration`**
4. `node --check app.js` 精确定位：

```
app/static/app.js:564
  const line=key,max,c=>pts.map(...)
                 ^^^
```

5. 第 565 行 `const area=key,max=>...` 同样问题

**根因**：`const line=key,max,c=>...` 写成了三个并列的常量声明（`const line=key`、`max`、`c=>...`），
而不是「箭头函数 + 解构参数」。**JS 里 `const f = a, b => ...` 永远不合法**。这是我写 chart 函数时的手误。

**修法**：加括号 → `const line=(key,max)=>...`，`const area=(key,max)=>...`

**为什么之前没发现**：
- `selftest.py` 只测 HTTP 端点，不测 JS 语法
- 浏览器**静默拒绝整个文件**，没有控制台报错被捕获（我最初 `agent-browser console` 返回空）
- 静态校验只查了「视图函数是否定义、页签是否有标题」，查不出语法错误

**已加防回归**：`selftest.py` 末尾接入 `node --check app/static/app.js`，
作为第 40 项断言（现在是「前端 JS 语法」）。找不到 node 时自动 SKIP 而非 FAIL。

**踩坑**：`check_js()` 里 `NODE = ... shutil_which_node()` 写在函数定义之前 → `NameError`。
Python 模块级代码按顺序执行，函数必须先定义再调用。已调整顺序。

## 三、智能路由引擎（新建 `app/router.py`）

### 设计
- `Target`：一个上游在某个模型下的运行时状态（延迟、EWMA、熔断、计数）
- `Router`：管理多个虚拟模型（`auto-fast` / `auto-weight` / `auto-priority`）
- 三种策略：`fastest`（EWMA 最低）、`weight`（权重优先）、`priority`（优先级降级）
- 熔断：连续 N 失败 → OPEN → 冷却 → 可再选
- 会话亲和：`aigw_session` 字段固定同一对话的上游
- 能力过滤：请求带 `tools` / 图片时自动排除不支持的

### 踩坑

**1. `probe_target` 里 `self.endpoint` 应为 `t.endpoint`**
```python
urls = [self.endpoint + "/models"]   # ❌ Router 没有 endpoint 属性
urls = [t.endpoint + "/models"]     # ✓
```
抛 `AttributeError: 'Router' object has no attribute 'endpoint'`，
后台探测线程直接死掉，`probe_all` 返回空。

**2. `Target.__slots__` 挡住了动态加属性**
测试里 `tg.capabilities = {...}` 报 `no attribute 'capabilities' and no __dict__`。
修：`__slots__` 补字段 + `__init__` 加 `capabilities=None` 参数。

**3. `probe_all` 去重导致部分 Target 永远没延迟数据（真设计缺陷）**

原实现按 `(upstream_id, endpoint)` 去重，只探第一个成员，其余成员的 `ewma` 永远为 None。
而 `fastest` 策略把「无延迟数据」的排在最后（改动前是排在最前，会抢跑），
导致某些上游看起来「延迟未知」被长期冷落。

修法：**按 endpoint 分组，探一次然后把结果回填给所有引用该 endpoint 的 Target**：
```python
groups = {}
for t in tgts:
    groups.setdefault((t.upstream_id, t.endpoint), []).append(t)
# work((uid, ep), members) → 探 members[0]，然后同步指标给所有 members
```

**4. 探测线程异常未捕获** → 单个上游探测炸了，整个 `probe_all` 抛异常。
修：`work()` 内 try/except + `join` 后检查存活线程数并记日志。

### 测试（新建 `test_router.py`）
起 3 个假 OpenAI 服务（不同延迟 30ms/120ms/300ms），另起两个故障服务
（429 恒失败、500 恒失败），验证 **21 项**：
探测排序、三种策略、429 降级、熔断触发、冷却恢复、4xx 不降级、
能力过滤、会话亲和、全熔断兜底、不存在模型、model 名替换。

**结果 21/21 通过。**

两个曾失败的用例分析：
- 「fastest 选中 mid」→ 探针去重缺陷（已修），不是策略逻辑问题
- 「冷却后转半开」→ 我的断言写错了。熔断期结束后 `pick` 应该**能选到**它，
  但 `state` 保持 `open` 直到下次成功/失败才改（这是正确的懒判断）。已改断言为「冷却到期后重新可选」。
