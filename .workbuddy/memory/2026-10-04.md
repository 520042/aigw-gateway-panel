## 一、问题定性：不是 bug，是 GUI 子系统的固有行为

`console=False` 的 PyInstaller 程序是 **Windows GUI 子系统**（PE Subsystem = 2），
本身**没有主窗口**。Windows 不会给无窗口进程分配任务栏位置，所以：
- 任务栏没有图标
- 没有窗口可以关闭
- 只能靠任务管理器杀进程

**解决思路**（两条腿）：

1. **设置 `AppUserModelID`** → `SetCurrentProcessExplicitAppUserModelID("AigwPanel.AIResourceHub")`
   让 Windows 把 exe 正确归组到任务栏，图标可固定/可分组。
2. **托盘常驻** → 自己建一个消息窗口 + 消息循环，`Shell_NotifyIconW` 挂图标，
   有了持续运行的窗口，图标就不会消失，右键菜单还能退出。

## 三、图标生成（不用 Pillow）

PyInstaller 的 `IconFile` **只吃 .ico 不吃 .png**（`struct.unpack requires a buffer of 16 bytes`）。

改成自己来：
1. `render(S)` 用解析式几何画：圆角矩形（圆角矩形 SDF 裁剪）蓝色渐变底 +
   白圆环 + 绿中心节点 + 三段外圈刻度弧（表示多上游路由）
2. `_png()` 手工构造 PNG（IHDR + IDAT + IEND，zlib 压缩，RGBA 8bit）
3. `build_ico()` 自拼 ICO 容器：`ICONDIR(6B) + ICONDIRENTRY(16B)×n + PNG 数据`，
   尺寸 ≥256 时 width 字节填 0（256 的低字节是 0），Vista+ 直接支持 PNG 压缩

抗锯齿用覆盖率混合：`_cov(dist, edge, aa)` 出 0~1 的覆盖率，`_blend()` 按覆盖率混色。

**踩坑**：`import math` 写在函数定义之后 → NameError。模块级 import 必须全在顶部。

## 四、ctypes 托盘的 5 个坑

**1. `ctypes.wintypes` 没有 `WNDCLASSW`**
`AttributeError: module 'ctypes.wintypes' has no attribute 'WNDCLASSW'`。
自己定义结构体，`lpfnWndProc` 用 `WNDPROC = ctypes.WINFUNCTYPE(LRESULT, HWND, UINT, WPARAM, LPARAM)`。

**2. 窗口过程回调必须保持引用**
`wc.lpfnWndProc = self._wndproc` 传的是 bound method，
ctypes 会临时造 CFUNCTYPE 对象，**赋完立刻被 GC**，随后窗口过程失效。
必须 `proc = WNDPROC(self._wndproc); self._proc = proc` 存住。

**3. `GetModuleHandleW` 在 kernel32 不在 user32**
`AttributeError: function 'GetModuleHandleW' not found`（在 user32 上找）。
同理 `ExtractIconExW` 在 **shell32** 不在 user32。

**4. `DefWindowProcW` 缺 argtypes → 整数溢出**
```
ctypes.ArgumentError: argument 4: OverflowError: int too long to convert
```
LPARAM 是 64 位，必须 `argtypes=[HWND, c_uint, WPARAM, LPARAM]`，
restype 也要设成 `c_ssize_t`（默认 c_int 会截断）。

**5. `CloseHandle` 缺 argtypes → HANDLE 被截断**
导致单实例互斥体释放不掉，测「释放后可再取得」直接失败。
`CloseHandle.argtypes=[HANDLE]` 后正常。
另外 `acquire()` 失败时**必须立刻 CloseHandle**，否则句柄一直占着。

**6. 气泡通知不能同步 sleep**
原实现 `Shell_NotifyIconW` 后 `time.sleep(9000)` 保持参数存活 → 调用方被阻塞 9 秒。
改成立即返回（NID 结构体是栈上的，函数返回前数据已拷走，不需要保活）。

**7. 海象操作符在 ctypes 参数列表里踩雷**
原本想用 `DWORD := ctypes.c_ulong` 简化声明，结果 `AttributeError`。
老老实实写全 `ctypes.c_ulong`。

## 一、登录按钮点了没反应 —— 根因是无限递归

**不是后端问题**：`/api/login?action=start` 实测 6 个平台全 200 + 正常 session。
**是前端架构问题**：

```
render()  →  loadExtra()  →  LOADERS[S.v]()  →  loader 末尾又 render()  →  ∞
```

**14 个 loader 全部**在末尾调 `render()`，而 `render()` 里又对
usage/checkin/login/route 四个视图调 `loadExtra()`。结果是：
- 切到「账号登录 / 签到中心 / 用量看板 / 智能路由」→ **请求风暴，页面永远停在「加载中…」**
- 切到其余 10 个视图（模型/站点/路由/设置…）→ `render()` 压根不调 loader → **数据永远是空的**

用户说的「模型导入不出来」「签到页面不对」同源。

### 修法（app.js）

```js
const S = { v:'dash', data:{}, busy:false, timer:null, loaded:'' };

function render(){                 // 只负责画
  const f=VIEWS[S.v]||VIEWS.dash;
  $('#view').innerHTML=f();
  if(S.v==='login')paintLoginSession();
}
async function switchView(v,force){ // 负责加载
  S.v=v; location.hash=v;
  $('#ttl').textContent=TITLES[v]||v;
  render();
  const loader=LOADERS[v];
  if(!loader)return;
  if(!force && S.loaded===v)return;  // 同视图不重复拉
  S.loaded=v;
  try{ await loader(); }catch(e){ toast('加载失败：'+e.message,'err'); }
}
```
导航点击改成调 `switchView(b.dataset.v)`；`DOMContentLoaded` 里 hash 路由同样走 `switchView`。

**实测效果**：切 login 页请求数从「无限」降为 `n1=4 n2=4`（800ms 后不再增长）；
连点 20 次 `render()` 发出 0 个请求。

### 回归测试

新增 `test_login_flow.js` + `test_login_flow_body.js`（29 项）：
- 递归回归：切页请求数上限、连点 render 不发请求、重复切不重拉、force 才重拉
- 登录全链路：点按钮 → fetch → 会话入 state → 二维码/授权链接 → 轮询启动 → 渲染
- Cookie 分支：粘贴框、我已登录按钮
- 取消、未知平台不崩

| 坑 | 现象 | 解法 |
|---|---|---|
| **测试自己的 sleep 被 stub 吞了** | `setTimeout` stub 成 `()=>0` 后，测试里的 `new Promise(r=>setTimeout(r,ms))` 永不 resolve → Node 事件循环空 → **零输出 RC=0**，像没跑 | 先存原生 `REAL_SET_TIMEOUT` 再 stub，测试用 `__sleep()` |
| `__dirname` 在 `vm.runInThisContext` 里 | 不在拼接脚本作用域内 | 拼接前先取好，body 只用传参 |

## 顺带挖出两个真 bug（WS 客户端）

| bug | 影响 | 修法 |

| **`connect()` 丢弃握手残留字节** | 服务端在 101 之后立刻发帧时（CDP 的 `Target.attachedToTarget` 等事件），TCP 会把它和握手响应粘在一个包里，`return cls(sock)` 时 `buf` 为空 → **这些帧被永久丢弃，后续 recv 全部错位** | `cli.buf = rest` 把 `\r\n\r\n` 之后的字节交给实例 |
| **`recv()` 漏处理 continuation (opcode 0x0)** | 真实 Chrome（CDP）的分片帧用的就是 0x0，漏掉 → 大响应永远收不齐 | 补 `elif opcode == 0x0` 分支 |
| 修 2 时引入的新问题 | 收到新 data frame 时 `self._frag = [payload]` **静默丢弃**未收完的分片 | 改成 append（宽容拼接），非标准分片也能合并 |

**为什么之前没发现**：分片测试用的是**非标准**帧（`0x01 FIN=0` + `0x81 FIN=1`，两个都是新 data frame），
恰好绕过了 continuation 分支。改成标准帧后立刻暴露。

**验证**：写独立最小复现脚本，7 种帧组合（标准三片/标准两片/单片/旧式两片/长帧 70000/

## 关键工程产出：端点动态探测器

**问题**：整站鉴权中间件让 404 探测法完全失效，401 不能当「接口存在」的证据。
按用户「拒绝看起来很像是级别的结论」的铁律，不能瞎猜路径写进 ACTIONS。

**解法**（`gwextra.probe_endpoints()`）：
1. 带登录凭据再扫一遍
2. **额外发一条「基准请求」**（故意用不存在的随机路径），拿到该站的「整站 401 指纹」
3. 只有当某路径的响应**与基准不同**时，才判定为真实端点
4. 404 直接判定不存在（对路径级路由的站点可信）

**实测验证**：
```
apk-coze      gated=False 基准=404 扫6 命中4  ← 与手工探测完全一致
apk-doubao    gated=True  基准=401 扫11 命中0  ← 正确识别整站拦截，不瞎报
apk-qwenwork  gated=True  基准=401 扫8  命中0  ← 正确
apk-kuku      gated=False 基准=404 扫6  命中0  ← 正确（确实没这些路径）
```

51 条候选路径 / 8 个平台。无凭据时明确拒绝并说明原因（`code: no_credential`）。

**根因**：网关 `/admin/api/models` **只有部分行**带 `availableAccounts` 字段，
31 个模型**全部**是 `None`；前端 `x.availableAccounts+' / '+...` 直接拼字符串。

**双端都修**（都做才稳）：
- 后端 `_merge_model_rates` 统一兜底：`availableAccounts/cnAccounts/intlAccounts`
  缺失转 int 0（非数字也不崩），`cnFree/intlFree` 缺失填 `"-"`，`cost` 缺失填 `"未观测"`
- 前端渲染也做 `Number(x.availableAccounts||0)` 兜底 + 全 0 时显示灰色 `0`

验证：修复后 `缺字段 0 个`。

## 一、模型选择：改成「生成客户端配置」而不是写进路由池

**先想清楚再动手**：`app/router.py` 里 `auto-fast/auto-weight/auto-priority` 是
**上游 target 的聚合**，不是「模型名白名单」。把勾选的模型硬塞进去语义不对，
自动路由的模型名会被覆写成 `target.model`。所以换了个更实用的落地：

- 勾选结果**持久化**到 `store.selected_models`（API `/api/models?action=select`）
- 工具条加「**生成客户端配置**」：一次生成 base_url + API Key + 模型清单 +
  Cherry Studio/NextChat 通用 JSON + Claude Code 环境变量 + curl 自测命令
- 没勾选时按「全选」处理，方便直接复制配置
- 复制有 `navigator.clipboard` + `execCommand` 双重降级
