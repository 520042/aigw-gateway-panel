## 一、问题定性：不是 bug，是 GUI 子系统的固有行为

`console=False` 的 PyInstaller 程序是 **Windows GUI 子系统**（PE Subsystem = 2），
本身**没有主窗口**。Windows 不会给无窗口进程分配任务栏位置，所以：
- 任务栏没有图标
- 没有窗口可以关闭
- 只能靠任务管理器杀进程

**解决思路**（两条腿）：

1. **设置 `AppUserModelID`** → `SetCurrentProcessExplicitAppUserModelID("AigwPanel.AIResourceHub")`
   让 Windows 把 exe 正确归组到任务栏，图标可固定/可分组。
2. **托盘常驻** → 自己建一个消息窗口 + 消息循环，`Shell_NotifyIconW` 挂图标，
   有了持续运行的窗口，图标就不会消失，右键菜单还能退出。

## 三、图标生成（不用 Pillow）

PyInstaller 的 `IconFile` **只吃 .ico 不吃 .png**（`struct.unpack requires a buffer of 16 bytes`）。

改成自己来：
1. `render(S)` 用解析式几何画：圆角矩形（圆角矩形 SDF 裁剪）蓝色渐变底 +
   白圆环 + 绿中心节点 + 三段外圈刻度弧（表示多上游路由）
2. `_png()` 手工构造 PNG（IHDR + IDAT + IEND，zlib 压缩，RGBA 8bit）
3. `build_ico()` 自拼 ICO 容器：`ICONDIR(6B) + ICONDIRENTRY(16B)×n + PNG 数据`，
   尺寸 ≥256 时 width 字节填 0（256 的低字节是 0），Vista+ 直接支持 PNG 压缩

抗锯齿用覆盖率混合：`_cov(dist, edge, aa)` 出 0~1 的覆盖率，`_blend()` 按覆盖率混色。

**踩坑**：`import math` 写在函数定义之后 → NameError。模块级 import 必须全在顶部。

## 四、ctypes 托盘的 5 个坑

**1. `ctypes.wintypes` 没有 `WNDCLASSW`**
`AttributeError: module 'ctypes.wintypes' has no attribute 'WNDCLASSW'`。
自己定义结构体，`lpfnWndProc` 用 `WNDPROC = ctypes.WINFUNCTYPE(LRESULT, HWND, UINT, WPARAM, LPARAM)`。

**2. 窗口过程回调必须保持引用**
`wc.lpfnWndProc = self._wndproc` 传的是 bound method，
ctypes 会临时造 CFUNCTYPE 对象，**赋完立刻被 GC**，随后窗口过程失效。
必须 `proc = WNDPROC(self._wndproc); self._proc = proc` 存住。

**3. `GetModuleHandleW` 在 kernel32 不在 user32**
`AttributeError: function 'GetModuleHandleW' not found`（在 user32 上找）。
同理 `ExtractIconExW` 在 **shell32** 不在 user32。

**4. `DefWindowProcW` 缺 argtypes → 整数溢出**
```
ctypes.ArgumentError: argument 4: OverflowError: int too long to convert
```
LPARAM 是 64 位，必须 `argtypes=[HWND, c_uint, WPARAM, LPARAM]`，
restype 也要设成 `c_ssize_t`（默认 c_int 会截断）。

**5. `CloseHandle` 缺 argtypes → HANDLE 被截断**
导致单实例互斥体释放不掉，测「释放后可再取得」直接失败。
`CloseHandle.argtypes=[HANDLE]` 后正常。
另外 `acquire()` 失败时**必须立刻 CloseHandle**，否则句柄一直占着。

**6. 气泡通知不能同步 sleep**
原实现 `Shell_NotifyIconW` 后 `time.sleep(9000)` 保持参数存活 → 调用方被阻塞 9 秒。
改成立即返回（NID 结构体是栈上的，函数返回前数据已拷走，不需要保活）。

**7. 海象操作符在 ctypes 参数列表里踩雷**
原本想用 `DWORD := ctypes.c_ulong` 简化声明，结果 `AttributeError`。
老老实实写全 `ctypes.c_ulong`。

## 一、登录按钮点了没反应 —— 根因是无限递归

**不是后端问题**：`/api/login?action=start` 实测 6 个平台全 200 + 正常 session。
**是前端架构问题**：

```
render()  →  loadExtra()  →  LOADERS[S.v]()  →  loader 末尾又 render()  →  ∞
```

**14 个 loader 全部**在末尾调 `render()`，而 `render()` 里又对
usage/checkin/login/route 四个视图调 `loadExtra()`。结果是：
- 切到「账号登录 / 签到中心 / 用量看板 / 智能路由」→ **请求风暴，页面永远停在「加载中…」**
- 切到其余 10 个视图（模型/站点/路由/设置…）→ `render()` 压根不调 loader → **数据永远是空的**

用户说的「模型导入不出来」「签到页面不对」同源。

### 修法（app.js）

```js
const S = { v:'dash', data:{}, busy:false, timer:null, loaded:'' };

function render(){                 // 只负责画
  const f=VIEWS[S.v]||VIEWS.dash;
  $('#view').innerHTML=f();
  if(S.v==='login')paintLoginSession();
}
async function switchView(v,force){ // 负责加载
  S.v=v; location.hash=v;
  $('#ttl').textContent=TITLES[v]||v;
  render();
  const loader=LOADERS[v];
  if(!loader)return;
  if(!force && S.loaded===v)return;  // 同视图不重复拉
  S.loaded=v;
  try{ await loader(); }catch(e){ toast('加载失败：'+e.message,'err'); }
}
```
导航点击改成调 `switchView(b.dataset.v)`；`DOMContentLoaded` 里 hash 路由同样走 `switchView`。

**实测效果**：切 login 页请求数从「无限」降为 `n1=4 n2=4`（800ms 后不再增长）；
连点 20 次 `render()` 发出 0 个请求。

### 回归测试

新增 `test_login_flow.js` + `test_login_flow_body.js`（29 项）：
- 递归回归：切页请求数上限、连点 render 不发请求、重复切不重拉、force 才重拉
- 登录全链路：点按钮 → fetch → 会话入 state → 二维码/授权链接 → 轮询启动 → 渲染
- Cookie 分支：粘贴框、我已登录按钮
- 取消、未知平台不崩

| 坑 | 现象 | 解法 |
|---|---|---|
| **测试自己的 sleep 被 stub 吞了** | `setTimeout` stub 成 `()=>0` 后，测试里的 `new Promise(r=>setTimeout(r,ms))` 永不 resolve → Node 事件循环空 → **零输出 RC=0**，像没跑 | 先存原生 `REAL_SET_TIMEOUT` 再 stub，测试用 `__sleep()` |
| `__dirname` 在 `vm.runInThisContext` 里 | 不在拼接脚本作用域内 | 拼接前先取好，body 只用传参 |

## 顺带挖出两个真 bug（WS 客户端）

| bug | 影响 | 修法 |

| **`connect()` 丢弃握手残留字节** | 服务端在 101 之后立刻发帧时（CDP 的 `Target.attachedToTarget` 等事件），TCP 会把它和握手响应粘在一个包里，`return cls(sock)` 时 `buf` 为空 → **这些帧被永久丢弃，后续 recv 全部错位** | `cli.buf = rest` 把 `\r\n\r\n` 之后的字节交给实例 |
| **`recv()` 漏处理 continuation (opcode 0x0)** | 真实 Chrome（CDP）的分片帧用的就是 0x0，漏掉 → 大响应永远收不齐 | 补 `elif opcode == 0x0` 分支 |
| 修 2 时引入的新问题 | 收到新 data frame 时 `self._frag = [payload]` **静默丢弃**未收完的分片 | 改成 append（宽容拼接），非标准分片也能合并 |

**为什么之前没发现**：分片测试用的是**非标准**帧（`0x01 FIN=0` + `0x81 FIN=1`，两个都是新 data frame），
恰好绕过了 continuation 分支。改成标准帧后立刻暴露。

**验证**：写独立最小复现脚本，7 种帧组合（标准三片/标准两片/单片/旧式两片/长帧 70000/

## 关键工程产出：端点动态探测器

**问题**：整站鉴权中间件让 404 探测法完全失效，401 不能当「接口存在」的证据。
按用户「拒绝看起来很像是级别的结论」的铁律，不能瞎猜路径写进 ACTIONS。

**解法**（`gwextra.probe_endpoints()`）：
1. 带登录凭据再扫一遍
2. **额外发一条「基准请求」**（故意用不存在的随机路径），拿到该站的「整站 401 指纹」
3. 只有当某路径的响应**与基准不同**时，才判定为真实端点
4. 404 直接判定不存在（对路径级路由的站点可信）

**实测验证**：
```
apk-coze      gated=False 基准=404 扫6 命中4  ← 与手工探测完全一致
apk-doubao    gated=True  基准=401 扫11 命中0  ← 正确识别整站拦截，不瞎报
apk-qwenwork  gated=True  基准=401 扫8  命中0  ← 正确
apk-kuku      gated=False 基准=404 扫6  命中0  ← 正确（确实没这些路径）
```

51 条候选路径 / 8 个平台。无凭据时明确拒绝并说明原因（`code: no_credential`）。

## app/localproxy.py —— 本机反代管理器

| 函数 | 职责 |
|---|---|
| `ensure_binary()` | 从 `sys._MEIPASS` 释放到 `data/cliproxy/bin/`，**size+stamp 双重记账**，二次调用 0.003 s |

## 一、托盘右键没反应 —— 真 bug（TrackPopupMenu 缺 WM_NULL）

代码里 `WM_RBUTTONUP` → `_menu()` 明明写了，但用户体感是「没反应」。

**根因**：`TrackPopupMenu` 返回后**缺 `PostMessageW(hwnd, WM_NULL, 0, 0)`**。
这是 Windows 托盘的经典坑 —— 没有这条，系统认为菜单没有前景归属，
**菜单会一闪就消失**。用户看到的就是「右键了但什么都没出来」。

```python
TrackPopupMenu(m, TPM_RIGHTBUTTON, pt.x, pt.y, 0, hwnd, None)
# 关键：返回后必须给窗口发 WM_NULL，否则菜单一闪就消失
PostMessageW(hwnd, WM_NULL, 0, 0)
DestroyMenu(m)
```

顺带补了 `WM_NULL = 0x0000` 常量（原来没定义）。

## 二、「为什么每次都开启 workbuddy-gateway」—— 说清楚它托管不集成

**workbuddy-gateway 源码不公开，是腾讯的独立程序，无法像 CLIProxyAPI 那样打进 EXE。**
面板做的是「托管它的进程 + 接管它的登录/签到/倍率/模型接口」，
`auto_start_gateway` 默认开是因为不托管你就得手动开。

已在设置页「自动拉起网关」旁加 title 说明，并在设置页写了一段说明（见下）。

## 三、冗余问题 —— 不是冗余，但给了用户选择权

# 二十二、端点真实性全量审计（基准对比法）

## 用户要求

> 「其他的关于登录后接入的代码，也都好好仔细全部审查一遍。」

起因是元宝那次「401 误判」，所以要把**所有平台**重新验一遍。

## 方法：基准对比

对每个站发两条请求：
- **A** 目标路径
- **B** **基准路径** —— 同站上一个肯定不存在的随机路径 `/__aigw_audit_<时间戳>__`

响应（状态码 + 归一化响应体骨架）**完全一致** → 该站的 401/404 是无信息量的通用响应，
**不能作为"端点存在"的证据**。只有 A ≠ B 才判定端点真实存在。

工具：`audit_endpoints.py`（结果落 `data/endpoint_audit.json`）

### 决定性发现：元宝的凭据不是 Cookie，是 hook 来的

`base(5).apk` 里有一段**注入到网页的 JS hook 脚本**（原样）：

```javascript
'use strict';
if (window.__yb2apiHooked) return;
window.__yb2apiHooked = true;
var last = '';
function report(h) {
    try {
        if (!h) return;
        var u = h['x-uskey'];
        var t = h['x-timestamp'];
        if (!u || !t) return;
        var key = u + '|' + t;
        if (key === last) return;
        last = key;
        Yb2ApiHost.uskey(JSON.stringify({
            uskey: u,
            md5: h['x-bus-params-md5'] || '',
            ts: t
        }));
    } catch (e) {}
}
```

**所以元宝要的是请求头里的 `uskey` + `x-bus-params-md5` + `x-timestamp`，
不是 Cookie** —— 这正是我之前用 CDP 只拿到 `qimei_` 设备ID 却调不通的根因。

豆包同理：除了 `sessionid`/`passport_csrf_token`/`msToken`，
还要字节的 **`x-tt-*` 签名头**。

### 面板当前的短板（诚实说明）

| 平台 | 我现在怎么拿凭据 | 对不对 |

## 续：豆包 apk-doubao 登录「Cookie 已取得但未通过登录校验」修复

## ★★ 豆包登录「Cookie 已取得但未通过登录校验」—— 第三次才找到真因（前两版判断均错）

赵亮原话（已不耐烦）：「怎么还是这个问题？到底能不能修好啊？」

### 前两版为什么错
- 第 1 版：归因为 CDP `cookie_header` 子串匹配丢子域 cookie。**修的方向没错**（那确实是 bug），
  但**不是这个症状的原因**——豆包失败的真正原因在验活端点。
- 教训：**先拿到"响应的证据"再下结论**。前两版都是"推测 cookie 没取到"，没去证伪
  "端点本身是否可用"。

### 决定性实验（这次的证据）
对 `https://www.doubao.com/api/v1/user/info` 发三组请求：
| 请求 | 结果 |
|---|---|
| 无 cookie | **401 + 空 body，Server: openresty** |
| 带完整假 session cookie（sessionid/sid_tt/passport_csrf_token…） | **401 + 空 body，完全相同** |
| 完整浏览器头（UA/Referer/Origin/sec-ch-ua/Sec-Fetch-*） | **401 + 空 body，完全相同** |

**真/假/无 cookie 响应完全一致** → 401 发生在 **openresty 网关层**，在应用校验 session 之前。
说明这些接口要 **`a_bogus` 签名**，签名算不出来就永远 401 → **cookie 再正确也过不了**。

补充探测（同样不可用）：
- `/api/v1/*`（user/info、user/profile、models、user/setting）→ 全部 401 空 body
- `/passport/web/user/info/` → 200 JSON 但要 `aid`：无 aid 返 `error_code:22「非法应用」`，
  乱填 aid 返 `16「该应用无权限」`
- `/samantha/*` → 404；`/v1/models` → 200 HTML
- `chat`(/samantha/chat/completion)、`image_gen` 无凭据也返 200 → **本来就不能验活**

**结论：豆包无法在线验活。** 不是 bug，是平台限制。

### 修复（build10）
1. `gwlogin.py` `apk-doubao.verify` 改成**离线会话标记判据**：
   `session_markers = [sessionid, sessionid_ss, sid_tt, passport_csrf_token, uid_tt, odin_tt]`
   —— Cookie 里出现任一标记（值非空）即通过；一个都没有 = 确实没登录，明确提示重登。
   新增 `_cookie_markers()` 解析 Cookie 串。
2. `verify_cookie()` **空 body 的 401/403 不再判"凭据无效"**：
   空 body = 网关层拦截（多因需签名），证明不了无效；只有带响应体的 401 才是应用层结论。
   （这条是通用修复，能防止其他平台也栽在同一个坑。）
3. `verify_cookie()` 支持 `session_markers`（离线验活通道），供其他"验不了"的平台复用。

### 验证
- 场景实测：真登录 cookie（含 sessionid/sid_tt）→ **通过**；
  只有设备 ID（ttwid/msToken，未登录）→ **拒绝并提示重登**；空 cookie → 不崩。
- `test_login.py` **343 → 348/348 通过**（新增 5 条：离线标记×3、空 body 401×1、豆包验活已改×1）。
- build10 重打包。

### 教训（写给以后）
- **"Cookie 已取得但未通过校验"≠ cookie 有问题**。先证伪端点：用「真/假/无凭据」三组对照，
  若响应完全一致 → 是端点/网关层问题，不是凭据问题。
- 空 body 的 401 是**网关指纹**，不是鉴权结论。

## ★★ 登录「没有记录」—— 用户追问后才补的端到端测试暴露的真 bug

赵亮原话：「你不仅是这一个登录没有记录吧？你好像所有的登录都没有记录。

### 补的测试：`test_login_e2e.py`（33 项）
覆盖三种登录方式的完整链路：登录 → finish(success) → `_save()` → `Accounts.add()`
→ 账号池可读回 → `usable()` 可取用。含全平台冒烟。
**核心不变量**：`success 必落库 / error 必不落库`（cookie 类平台用假 cookie 时

### 测试暴露的两个真 bug
| # | 问题 | 影响 |
|---|---|---|
| 1 | **`call()` 缺「网关本地凭据」兜底** | 文档写了优先级「指定账号 > 可用账号 > **网关本地凭据**」，但代码里**从没调用** `_secret_from_gateway_files()`（只在拉模型目录时用了）。而二维码登录存的 secret 是**空串**（凭据在网关），`usable()` 会过滤掉空 secret → **wb-gateway / apk-trae / apk-codebuddy / apk-codebuddy-cn 登录后所有接口都报「账号池里没有可用凭据」**。用户明明登录成功，功能全废 —— 这就是"登录了却没记录"的真实体验 |
| 2 | **`_save()` 静默吞异常** | `except Exception: pass` + `if not self.accounts` 直接 return，落库失败毫无痕迹，表现为「登录成功但没记录」且查不到原因 |

### 修复
1. `gwextra.call()`：先单独判「该平台有没有 gateway 型登录记录」（允许空 secret），

2. `gwlogin._save()`：不再静默吞异常 —— `accounts` 为空时记 `save_error`；
   `add()` 抛错时把 `type+msg` 写回 `result["save_error"]`，接口/测试可查。

- **状态机测到 success 不等于功能可用**，必须测到「数据落地 + 下游取得到」。
